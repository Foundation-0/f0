Instruments · for one person and their agents

A lab’s worth of instruments, for one person

A language model on its own reads text and writes text. Everything else a scientist needs, from a notebook to a budget, has to be built around it. This page explains that surrounding machinery from first principles, and the four instruments that we and our founding members are building.

Exo · private preview Auto-research-agent · released autofoundry · open source v0.1 As of 14 Oct 2026

00//From first principles

Plain words first

The model is the engine. The harness is the car.

A large language model is a program that has read a vast amount of text and learned to continue it. Give it some text and it writes more. That is all it does. It cannot open a file, run a test or remember yesterday. It does not know what its answer cost, or which version of itself produced it. Each request starts from nothing but the text sent with it, and that text has to fit in the model’s context window: the most it can read at once.

So everything useful about an AI system lives outside the model, in the software around it. That software is called a harness, like the straps that let a horse pull a cart. We prefer a car. The model is the engine: powerful, and useless on its own. The harness is the rest of the car. Tools are the wheels and the steering. Permissions are the brakes and the seat belt. The record is the logbook, memory is the driver’s sense of the road so far, and the cost meter is the fuel gauge.

Two definitions

Harness: the software around a model that gives it memory, tools, records and limits. Exo’s own site puts it in nine words: “the code around a model that lets it act.”

Agent: a model running in a loop inside a harness. It reads, chooses an action, the harness carries the action out, and the result goes back in as text.

Why this matters to someone working alone

A university lab gives a scientist more than equipment. It gives them a notebook others can audit, colleagues who remember last month’s dead ends, a safety officer, technicians, and a grant office that tracks what was spent. An independent researcher has none of these.

Yet people working alone or in small groups have lately been producing large, checkable results with AI. On this site, founding member eumemic used an AI coding agent to search NASA data on more than four million stars and by 14 October 2026 counted 665 small-planet candidates (not yet confirmed) that the official searches had passed over. In a public race started by founding member Doug Colkitt, people and their agents took a saving in fast multiplication from 2−182 to about 2−9.2 in a week, every step checked in exact arithmetic, though all of it still rests on a machine-written paper nobody has yet reviewed. Each of those results came from a person, a model and a harness. When the harness is good, one person can work like a lab. When it is poor, the work is hard to repeat, hard to credit and easy to get wrong.

01//Exo · Aska Digital

Private previewEarly build · no outside reviewOpen source when ready to ship

Exo: one agent, one memory, one record, and consent to the exact words.

Exo is the harness Aska Digital is building, first for its own daily work. Its central idea comes from accounting: keep a record that can only grow, and work out everything else from it.

Sealed until release, like Seldon’s Time Vault

What it does, in four ideas

  1. Start from a record, not a memory. Every meaningful event (what you said, a rule you gave, what an agent did, whether you accepted it) is added to a log that is never edited. Each entry is signed and carries the fingerprint of the entry before it, so changing any old entry breaks every link after it. Everything Exo believes about you is computed from that record, the way a bank balance is computed from the transactions. Whitepaper §3
  2. One agent, one continuous memory. Every window, scheduled run and message from another agent is a thread of one agent with one log. Each turn is a fresh request built from summaries plus the latest messages. See it work below.
  3. Ask by consequence, and bind consent to the exact words. Private steps that can be undone run at once and are logged; anything public, irreversible, paid or touching other people waits for you, and your yes covers a fingerprint of those exact words. Try it below.
  4. A harness that watches itself. Every model call records which model was asked for, which one answered, each failed try, the wait for the first word, the tokens and the cost. Plain rules read that record after each turn and file findings; a fix counts only after 20 quiet turns or 3 days. A price Exo does not know reads “unknown”, never $0. §9, §13.5

What nobody outside can check yet

The code is private during the early build (“Access to the repository is limited during the early build”), so the test counts above are Aska’s own and cannot be reproduced from outside. There are no benchmarks and no outside review, and the whitepaper says so: “Nothing in this paper reports a benchmark, an accuracy figure or a speed-up for Exo itself, beyond the small live checks named above.” Aska will publish the source when it is ready to ship.

How it is built

Exo is made the way it describes. In the whitepaper’s words: “In each wave, parallel agents own disjoint paths and do not commit. A lead reviews, runs the full suite, and commits.” Its mark is drawn from Aska’s incentre lattice, another project on this site.

02//Explainer · the gate

Illustration · not the Exo software

Consent to the exact words.

An assistant that asks about everything trains you to click yes without reading. One that never asks can push, post or pay in your name. Exo’s answer has two halves: ask only when an act cannot be undone or reaches other people, and when it asks, make your yes cover those exact words and nothing else.

The trick behind the second half is a hash: a short fingerprint computed from a piece of text, which changes completely if a single character changes. When Exo asks, it hashes the exact text, title, target, tool and arguments, and your answer covers that hash only. The figure below computes a real SHA-256 fingerprint in your browser as you type.

03//Explainer · the summary tree

Illustration · simplified

Memory that stays one page long.

Most chat apps send the whole conversation with every request, so each request is longer than the last, until it no longer fits. Exo builds every request fresh: summaries of the old, and the latest messages word for word.

The whitepaper’s picture is a long book. “To keep reading well you need the summaries of everything so far, plus the last few pages in full.” The last 12 messages travel verbatim (word for word). Older messages are cut into leaves of 8, and each leaf gets one short summary. When the summaries together pass a budget of 6,000 tokens (the word-pieces a model reads; Exo estimates one per four characters), the oldest pair of neighbouring summaries at the same level merges into one, a level up. Nothing is thrown away: every original message stays in a local database you can search.

04//Explainer · the climb

Illustration · not the Exo software

Learning that has to beat the noise.

Exo’s site promises a model fitted to you. Its whitepaper says how a lesson earns its place: a change is kept only if it scores better on an exam built from your own past decisions, by more than the exam’s own wobble, and does not score worse on questions the process never saw.

The exam is personal: questions about you with known answers, pairs of a reply you rejected and the one you chose, and real past moments cut off just before you gave your verdict. It is split by time. The oldest part is train, which the reviewer may read. The middle is dev, where each candidate change is scored. The newest part, plus a fixed 20% sample, is held out: the loop never reads it, and uses it only for the final keep-or-drop. The whitepaper’s picture is a hillside in fog: you cannot see the top, but you can tell whether one small step takes you higher.

Why hold anything back? In the whitepaper’s words, “any process that tries many small changes and keeps the ones that score better will, given enough tries, find changes that fit the quirks of the test rather than the person.” Turn the held-out check off below and watch that happen.

What the figure leaves out

Not every lesson goes through this gate. A rule you state yourself is kept at once, and the whitepaper says that if you ruled a lesson, it is kept even when the exam disagrees: “the person outranks the eval”. An unguarded taste with strong evidence from two separate sessions is promoted without the climb; skill changes must pass it. Today’s climb builds two kinds of candidate, adding one held-back lesson or dropping one auto-promoted lesson, and the trigger that would run it every night by itself is not built. The whitepaper reports no eval scores, and warns that a small personal exam is noisy, so the band “may reject most changes until the set grows.” Sources: §6, §22.3, §22.5, §32.

05//Exo OS · Aska Digital

Private previewPhase 0 · research and designOpen source when ready to ship

Exo OS: the same core, as an operating system.

An operating system is the layer of software that decides which program may touch which file, device or key. Isolation lives there. Exo OS asks what an operating system looks like when an agent like Exo is its foundation, not an app on top.

The public record is short, and we keep to it. Exo OS runs the same core and the same protocol as Exo, with no fork, in its own repository. Phase 0 is research and design of the base system, the shell, security and small hardware; the operating system “is meant to supply the isolation.” The whitepaper (version 0.2, October 2026) is blunt about the rest: “nothing of it is built, and no machine runs it.”

Since that whitepaper, one piece has moved from design into code. The roadmap’s evidence panel of 13 October 2026 says: “Exo OS can now require every tool call to pass through an installed execution broker” (a separate program that carries out approved actions), while “the operating-system sandbox behind it is still being built.”

06//Auto-research-agent · rohanarun

Released softwareMIT licenceFounding member’s project

Auto-research-agent: send your own agent to an open problem.

Founding member rohanarun’s Mac app makes it, in its README’s words, “dead simple to point your Codex or Claude at open problems, put unused tokens to work, and help push the frontier.”

A sidebar lists open research projects from a catalog, “Auto Research by Super”: GitHub repositories that publish an auto-research.md guide written for agents. Press play and the app clones the project, hands the guide word for word to the coding agent you already have (OpenAI Codex or Claude Code), and shows the conversation live. It also shows each project’s latest claim and a small chart of its progress.

Optionally it runs several agents at once. On a timer it stops them, asks the model to merge what they found into one shared summary, and starts fresh agents from that summary. The defaults are 2 agents and a 10-minute interval.

Every agent also gets the same research policy, which reads like a lab’s code of conduct. It asks agents to keep formal proofs, exact finite checks, measurements, conditional results and a maintainer’s acceptance apart, and never to weaken a check to make a candidate pass. Its plainest line: “Never manufacture a record, passing check, publication, or external outcome.”

Status, plainly. Released software, not a research result. The README says the downloadable version 1.2.3 is “Developer ID signed and Apple notarized”. It was published on 13 October 2026 (12 commits that day), MIT-licensed, written in Swift with no third-party Swift dependencies. No research result made with the app is documented yet.

The member behind it

rohanarun builds software that lets AI coding agents work on open research problems. Working with Codex and Claude, they are the most active contributor to the integer-multiplication race, and they hold the current reviewed record there: PR #1094.

07//autofoundry · Ryan Shea

Open-source software · v0.1.0MIT licenceFounding member’s project

autofoundry: one experiment, many rented machines.

Training a small AI model is now cheap enough that an agent can run hundreds of short experiments. The hard part is renting the hardware. Founding member Ryan Shea’s command-line tool does that across four clouds.

A GPU (graphics processor) is a chip built to do many small calculations at once, which is exactly what training a model needs. Cloud companies rent GPUs by the hour, each with its own sign-up, prices and quirks. In Andrej Karpathy’s autoresearch, AI agents edit a training script and re-run it on their own; the README calls autofoundry “a CLI companion” to it. You name a script and a GPU type, and autofoundry:

  1. searches four providers (RunPod, Vast.ai, PRIME Intellect and Lambda Labs) for matching machines, and rents them;
  2. copies the script over, runs it and streams the output back live;
  3. collects whatever numbers the script prints after a --- line;
  4. reports the best, mean and worst result across the runs, and shuts the machines down.

Why does the spread matter? Training involves chance: the same script on two identical machines rarely gives the same number. One run is one sample. Several runs show how much the result wobbles, and a change is only worth keeping if it beats that wobble. That is the habit of every good lab, made cheap.
