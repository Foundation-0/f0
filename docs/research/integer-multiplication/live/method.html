Tracker · how it works

Method

Back to dashboard. What the tracker counts, what it will not call verified, and how its feed is made and checked.

What “conditional κ” means

Upstream CrocSwap/integer-mult-bounds races an asymptotic integer-multiplication bound of the shape T(n) = O(n (log n)^(1−κ)). Every κ published there is conditional: it holds only given the retained interfaces the construction inherits (all-size compiler, weighted/common-ancestor chart, restored rows, selectors/routing, prime supply, precision/recovery, complex symbolic correctness, analytic transfer). A larger κ is better. It is not an unconditional multiplication-exponent theorem, and this dashboard never presents it as one.

Tiers

  • claimed — default. Any open upstream PR whose title/body carries a parseable κ value (exact fraction and/or decimal). Draft PRs stay claimed and render hollow-grey; they are never promoted.
  • human-verified — only when a PR’s exact (κ fraction, κ decimal) matches upstream certificates/selected-result.json on main (maintainer-reviewed checkpoint, bound by its certificate_sha256). v1 expects exactly one such point.
  • lean-verified — reserved; requires a Lean formalization artifact. No upstream PR has one today, so v1 ships this set empty (schema support only).

Plain words, added on Foundation0

“human-verified” is the feed’s tier name, kept for compatibility with feed.schema.json. It means maintainer-reviewed and conditional: the race’s maintainer has re-run the exact certificates and selected the value. It does not mean peer reviewed, and it does not mean a complete Lean proof. The dashboard labels it “maintainer-reviewed” for that reason.

Quarantine policy

A record is quarantined (stale: true) when its stated fraction and decimal disagree beyond 15 significant digits, when a κ-looking claim is unparseable, or when its head SHA changed without a successful re-fetch. Quarantined records stay in data/records.json and under feed.json’s quarantined[] (never silently deleted) but are excluded from the chart step-line until re-resolved.

Record key and staleness

One record per (PR × head SHA): any force-push creates a new record; old rows are retained append-only. fetched_at and pr_updated_at drive the age display; the red banner is always-on because the race moves roughly every ten minutes and nothing served here is a live quote.

Since the move to Foundation0, the dashboard also reads the race’s own certificates/selected-result.json live in your browser and shows it at the top, labelled with the time it was fetched; when this feed is more than a day old, it says so beside that value.

Pipeline

A 15-minute GitHub Actions cron (.github/workflows/update.yml) runs scripts/fetch.py (upstream REST, conditional ETag requests) then scripts/gate.py: schema validation, byte-determinism re-emit, selected-result binding, and claimed/verified separation. Only if all four pass does the workflow commit the regenerated docs/feed.json and docs/chart-data.json; a failed run changes nothing and the last good state stays live. Parser behaviour is golden-file-gated on PRs #419/#425/#431/#433 (tests/golden_kappa_parse.json, tests/run_golden.py).

Schema reservations (v2, additive)

feed.schema.json already permits project_id, claim_id, machine_checked, ai_refereed_count and feed_version: 2 for the planned multi-project feed (integer-mult-kappa, threesum-derand, mobius-x1). v1 producers emit none of them.
